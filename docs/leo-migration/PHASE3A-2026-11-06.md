## Execution contract

`dispatchLeoExecution` preserves the n8n compatibility adapter for existing operations. The only new provider capability is `leo.crm.followup.send`, enabled explicitly with `LEO_CRM_FOLLOWUP_PROVIDER=trigger_dev`. There is no arbitrary task-name routing or fallback to n8n on enqueue failure.

The new capability accepts exactly organization_id, agent_id, customer_id, message and optional channel=whatsapp. IDs identify canonical CRM records. It sends approved text within a verified inbound 24-hour customer service window. It rejects hotel and real-estate organizations; their booking revisions, guest consent, domain templates and existing approval stores retain their specialized paths. Appointments, campaigns, workflow lifecycle and other n8n dependencies remain separate migration work.

1. The existing server resolves identity, tool permissions and organization targeting.
2. The first call issues a five-minute, server-stored approval bound to principal, tenant, channel, session and canonical action digest. Caller `confirmed` booleans do not authorize execution.
3. A second explicit confirmation carries the token. Chat and voice retain tokens in memory and omit them from model outputs and stored conversation history.
4. The dispatcher verifies the signed envelope before accepting execution. Fresh tenant permissions are supplied to the existing verifier because permission sets are not carried in the v2 envelope. The CRM proof also signs the principal in the argument hash; legacy envelope signatures do not cover email.
5. A service-only SQL function locks and consumes the approval and creates the execution atomically. Exact retries return the original execution, including after broker deduplication TTL. Changed actions, principals, sessions and channels fail closed.
6. Trigger receives only the execution ID with stable key `leo-crm:<execution-id>`. Broker acceptance returns queued/HTTP 202. An ambiguous enqueue returns enqueue_unknown and the same durable ID for reconciliation. It never falls back to another sender.
7. The worker reloads the service-only record, checks its consumed approval binding and 15-minute authorization deadline, refreshes membership/permissions or configured admin identity, and validates current organization, agent and customer bindings, feature entitlement, service window and handoff state.
8. Compare-and-set claims prevent multiple workers from entering delivery. A persisted sending marker precedes the provider call. Provider uncertainty is terminal unknown, with no automatic resend. Worker crash during processing/sending requires manual reconciliation; task retries are disabled.
9. Completed means the worker has persisted a provider message receipt. The result explicitly says provider_accepted, not delivered. CRM logging occurs after durable acceptance and cannot cause resend. The private status endpoint checks the initiating principal and current tenant permission; overdue nonterminal records return reconciliation_required.

## Staged setup and verification

- Apply `20261106161658_leo_crm_trigger_executions.sql` to a disposable/staging database first. Tables have RLS and service-role-only grants; no public/tenant direct access to approval or execution evidence.
- Use a staging Trigger project/environment with the same database, dedicated `LEO_EXECUTION_SIGNING_SECRET`, current membership data, configured admin email if used, and tenant-scoped WhatsApp credentials. Deploy `leo-crm-followup-v1` there before enabling its adapter in the application preview. Keep the flag off in production.
- Confirm that test tenants are neither hotel nor real estate, the agent is active/published, a canonical CRM customer has a recent inbound message, no handoff is active and follow_ups is entitled.
- Prepare via chat and voice. Confirm that first calls return confirmation_required without enqueue, changed arguments cannot use an old token, and boolean-only confirmation does not send.
- Approve once; inspect queued/HTTP 202, poll `/api/leo/executions/<id>`, correlate execution ID to the Trigger run, and verify the provider receipt. Replay the same approved call and deliver a duplicate task: neither may send again.
- Revoke membership/permission, pause tenant/agent, expire authorization, change approval binding, close the customer window and simulate provider timeout. Confirm no unauthorized send and no resend after an unknown outcome.
- Smoke-test current Maia calls, hotel setup and tenant preview navigation separately. No live external message or voice call should be claimed verified from mocked tests.

No migration, Trigger deployment, production flag, merge or promotion is performed by this PR. A Vercel application preview alone does not prove the separately deployed worker or real WhatsApp delivery.
